# Architecture

One crate, one binary (`invoice`), one Postgres database, one embedded SPA.

```
invoice serve            → migrations up → Axum server (API + SPA) on INVOICE__BIND
invoice migrate up|status|down [-n N]
invoice storage migrate --from-dir <dir> [--design-dir <dir>]   → copy an fs archive (+ old design dir) into the configured storage
invoice design push <dir> | pull <dir> | ls | rm <path>… --space <slug>  → design overrides of a space (`spaces/{id}/design/…`)
invoice openapi          → print the OpenAPI document (no config needed; `make frontend-api-types`)
```

The `storage` command needs only the storage settings (`INVOICE__STORAGE_KIND`, `…_DIR`, `INVOICE__S3__*`; with
`INVOICE__DATABASE_URL` it also re-records every space's design storage usage afterwards); `design`
also `INVOICE__DATABASE_URL` (slug → space id). There is no CLI user / space creation: bootstrap = registration.

Domain modules follow a simplified nexial/infra pattern: `src/<module>/{mod.rs (router), entity/, repo/, handlers/}`
(handler files hold their DTOs + validation; repos take validated DTOs). `document/` is split further: domain
types in `model` / `snapshot` / `meta`, wire shapes shared with MCP in `wire/`, operations shared with MCP in
`service.rs`; its `handlers/` is axum-only (`layering_tests.rs`). Routers are mounted in `app.rs` behind the auth
middleware and registered in `openapi.rs`. They share `AppState`, `error.rs` and `validation.rs` instead of
per-module config/error files. Migrations live in `src/migration/`.

Invariants enforced in the database as well as in the repos: one company row (`CHECK (id = 1)`), at most one
default bank account per currency and one default VAT rate, which must be active (partial unique indexes; repos promote a replacement
so a non-empty group always has exactly one), unique VAT rate value, unique contact IČO when not null. Multi-row
writes run in `db.transaction(|txn| …)`, which awaits the rollback on error. `allocate_number` is an atomic
`INSERT … ON CONFLICT DO UPDATE … RETURNING` on `number_series_counters` and must run inside the transaction
that stores the numbered document.

Documents: totals are recomputed by `compute.rs` on every save and at issue and stored (`documents.total_*`,
`payable`, `total_czk` + `document_vat_recap`); reads return the stored values. `documents.paid` is re-summed
from `payments` in the payment transaction; `paymentState` / `overdue` are derived on read (and mirrored as SQL
conditions for list filters). Every state-changing write locks the document row (`SELECT … FOR UPDATE`) before
checking its status. Issuing calls ČNB before opening the transaction and refuses (409 `conflict`) if the draft
changed meanwhile. Money arithmetic in `compute.rs` is checked; overflow is a 422. The counter `PUT` locks the
counter row before its below-issued check, serialising with `allocate_number`. Unique `(doc_type, number)` per direction (imported drafts included; a native issue that collides → 409 `number_taken`); contact / bank account FKs are
`ON DELETE SET NULL` (issued documents keep their snapshots), lines / recap / payments cascade.

Advances (1c): a payment on an issued proforma whose supplier snapshot is a VAT payer in `standard` mode issues a
DDPP in the same transaction (rate resolved before it; ČNB failure → 422 and nothing stored). A DDPP's recap comes
from `ddpp.rs` (VAT from above) and is stored as is — DDPPs are created issued and never pass through save/issue,
so nothing recomputes it from base × rate. DDPPs have no payments, cannot be edited or cancelled directly; deleting
the payment cancels its DDPP unless an invoice deducts it (issued: 409 `advance_settled`, draft: 409 `advance_in_use`). `advance` lines store a
snapshot of the deducted amounts (`advance_recap`), refreshed and re-validated at issue; every write holding
advance lines locks the deducted documents (id order) and re-checks they are issued and not on another
non-cancelled invoice. Lock order is always owning document → referenced documents (invoice → DDPP/proforma,
proforma → DDPP, correction → its original). Credit notes and DDPP corrections are stored positive (`sign = -1`), keep the invoice's rate
(`exchange_rate_source = 'original'`), and issuing one locks the invoice before the per-rate cap check.

PDF (1d): no transaction, row lock or pooled connection is held across an mdcast render or SMTP, and document
writes (issue, archive, originals, imports) never hold one across a storage call. Exceptions, by design: the design
editor holds its lock transaction across storage copies / deletes ([api/design.md](api/design.md)) and lifts the
pool's `idle_in_transaction_session_timeout` for that transaction (`db::allow_idle`). The CSV / accounting exports
build the whole file inside their read-only snapshot, commit, and only then send it.
Issuing (`document/repo/issue.rs` + `issue_apply.rs`) runs the issue in a dry-run transaction that is rolled back,
renders that payload and puts it under a new per-attempt key (`documents/{year}/{id}-{sha8}-{nonce}.pdf`) outside any
transaction, then applies the issue again in a short transaction that commits only if it yields the same payload
(else the object is removed and the issue starts over: once for a draft edit, then 409 `conflict`; up to 5 times
with a jittered backoff when only the number was taken); a render failure issues nothing and
uses no number, a failed commit removes the object (`original::remove_unreferenced`). Original uploads and imports
put their per-attempt object before their transaction the same way; a crash between put and commit can leave an
unreferenced object (no sweep yet). The payment that auto-issues a DDPP never
fails because of PDF: after its transaction commits the handler spawns one archive attempt (background, the 201 is
not delayed); otherwise the first `GET …/pdf` does (render + put, then `UPDATE … WHERE pdf_path IS NULL`; the loser
removes its object and serves the stored file). A cancelled document without an archive renders with the "STORNO"
watermark and no QR. The pool is bounded by `db.rs` (size, acquire timeout, server-side statement /
idle-in-transaction timeouts); render concurrency / preview limits are deferred for the invite-only test phase
([api/pdf.md](api/pdf.md) Clarifications).
Archives are immutable. Default design: repo `design/` (`invoice.typ` + Inter TTFs + OFL),
embedded in release builds (debug builds read it from disk).

Received & import (1e): received documents have no draft — `POST` records them (`status = issued`) and allocates the
internal number from the doc type's `received*` series for the `receivedDate` year in the same transaction; `PUT` /
`DELETE` work in any status (number never changes; delete removes payments by cascade and the original file after the
commit). Their recap is entered and stored as is (`document_vat_recap`), never recomputed. The ČNB rate for
`receivedDate` is fetched before the transaction and kept while currency and `receivedDate` stay the same. Received and
imported documents never issue DDPPs, never get a rendered PDF, and are excluded from advance deductions. Imported
issued documents are drafts with their own `number`; issuing them allocates nothing and renders nothing. Custom field
values (`documents.custom_fields`) are validated on every save, at issue and by `PUT …/metadata`.

Corrections (1f-a): debit notes raise the credit cap of their original (cancelling one is refused with 409
`exceeds_original` when the issued credit notes would exceed the lowered cap). A DDPP correction locks the DDPP at
create / issue / cancel and is refused while an invoice deducts the DDPP; its full correction takes the DDPP's
remaining VAT (and CZK amounts) instead of `round2(base × rate)`, so `advance` lines deduct the DDPP's recap minus
its issued corrections and a fully corrected DDPP is skipped. A DDPP with a live correction keeps its payment.

## Frontend (`frontend/`)

Vue 3 + TS + Vite + Tailwind v4 + Pinia + vue-router + vue-i18n (cs default, en).

Feature code lives in `src/features/<feature>/` with `api.ts` (calls through `request()`),
`types.ts` (wire types — decimals as strings, nullable fields as `| null`; response types alias the
generated schema via `src/api/wire.ts`, request bodies are hand-written), Pinia store(s),
`views/` (routed) and `components/`. Form state is all-strings "drafts"; each feature has
`toDraft` / `validate*` / `to<Wire>` helpers so conversion and client-side checks are unit-tested
outside components. Client validation is light (required, length, IČO checksum, pattern);
the server's 422 stays the source of truth and its `fields` are shown inline.

## Build, CI, image

- `Dockerfile`: node:22 builds the SPA → `rust:1.97.0-bookworm` builds the release binary with the SPA and `design/` embedded (`--locked`) → `debian:bookworm-slim`, non-root uid 10001, `INVOICE__STORAGE_DIR=/data` (`VOLUME /data`, owned by 10001; unused with `INVOICE__STORAGE_KIND=s3`), `EXPOSE 3000`, `invoice serve`.
- `.github/workflows/ci.yml`: PR + push to `master`; backend job (Postgres service, `TEST_S3_*` from secrets, `libxml2-utils` for the ISDOC, Pohoda and Money S3 `xmllint --schema` checks, `make lint-backend test-backend`, toolchain pin check), frontend job (`make frontend-install lint-frontend test-frontend frontend-build`); the backend job also sets up Node and runs `make frontend-install api-types-check` (the generated `frontend/src/api/schema.d.ts` must match the backend's OpenAPI).
- `.github/workflows/docker.yml`: `v*` tag → `ghcr.io/xmiksay/invoice:<version>` + `latest`.
- Deployment manifests are out of scope for now.
